# 卡片首段回复出现时的内部位移

日期：2026-11-03。工作树基线：`a64a6ad`。

## 录屏观察

用户提供的 `录屏2026-11-03 16.29.19.mov`：4096×2502，时长约 9.05 秒，
H.264，SHA-256：`76bdd9a0398e035ac045440f03a48e43c3cd4dd54653e4767b8b6b433168edc2`。
Apple AVFoundation 在当前环境解码失败，改用临时目录中的 FFmpeg 解码。
检查了全片逐秒画面及 3.000–3.333 秒的相邻原始时间戳帧。

| 时间 | 右上卡片的可见变化 |
| --- | --- |
| 2.800s | 两行提示标题；模型、计时器；「正在执行／回复会显示在这里」 |
| 3.000s | emoji 已变更；标题和上述内容的位置仍保留 |
| 3.100s | 旧标题淡出；首段英文回复开始出现，模型、计时器尚未上移 |
| 3.133–3.283s | 新生成的短标题进入，标题由两行变为一行；模型、计时器和正文整体上移约一个标题行高 |
| 3.500s | 短标题和首段回复稳定；后续正文继续更新 |

前后卡片外框、右上徽章锚点以及相邻卡片没有对应位移。
这是「尚无回复 → 已有首段回复」伴随生成标题更新的内容变化，
不能从画面认定执行已经完成。占位说明带图标列，实际正文从正文左缘开始；
两种内容的横向起点不同，不是模型、计时器整体纵向跳动的原因。

## 根因与改动

真实生产路径为 Codex Overview → 共享
[HarnessThreadCard / ThreadCardIdentity](../app/macos/Sources/Shared/PluginUI/Cards/HarnessThreadCard.swift)。
标题、模型、用时和正文在同一个从顶部排列的 VStack 中。
`CardTitleSwap` 保留了文字的淡出／淡入，但原先 `.lineLimit(2)` 只限制最大行数，
不保留第二行；其 displayed 文本换成一行时，下方所有内容重新排列。
[ThreadCardBody](../app/macos/Sources/Shared/PluginUI/Cards/ThreadCardInitialResponse.swift)
替换占位的同时发生了标题更新，使位移看起来像状态切换引起。

标题现在使用 `.lineLimit(2, reservesSpace: true)`，并以纵向 fixedSize
保留实际字体测出的两行高度，避免较长正文竞争纵向空间时再次压缩标题。
没有新增硬编码标题高度、叠放的隐藏副本、历史高度缓存或状态相关尺寸。
原来的两行长标题、完整标题 tooltip/辅助功能文本、正文行数上限、请求控件和卡片外部尺寸契约均保留。
短标题现在会留下第二行空白，因此相比以前的一行紧凑布局，可能少显示一行摘要；
这是稳定内部锚点的明确取舍。摘要仍按可用高度和原有行数上限截断，完整内容由阅读页承担。
