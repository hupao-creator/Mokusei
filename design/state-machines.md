# State machines in Chief

The same Agent Thread can have a finished foreground execution, running background work and a pending input. Those facts answer different questions. For Stop, Runtime decides whether there is work to stop while holding the Thread’s cancellation gate. Moku and Overview consume the acknowledgement of that request. The Thread record separately identifies which execution actually ended and who requested its interruption. [Runtime contract](../internal/core/runtime/README.md)

## How to read the inventory

Each row follows a production lifecycle whose next action depends on a previous event. The middle column identifies the state encoded by flags, optional values, receipts, tasks, generations or ownership records. This includes the implicit parts of workflows that already name some phases with an enum. Rows group instances that share an owner and transition rules, such as one content subscription per execution or one animation clock per visible card.

The inventory covers the Go service, macOS host, four built-in Harness adapters, Applications, Context plugin and Sidecards. It follows their production source and public observations. External engines and operating-system frameworks appear at the callbacks Chief owns. Demos, build tools and verification runners have separate lifecycles. The linked modules own the detailed contracts. The [verification index](../tools/verification/facts.md) identifies executable coverage and its limits.

## Verification

Follow a row from its owner to the boundary that can observe the disputed transition. For Stop, the routine admission property reads the Runtime acknowledgement and the committed Thread after generated send histories and a repeated stop. The opt-in system property reads the actual tool result delivered through native Codex for a finished Thread, a missing target and the repeated Thread. Desktop journeys exercise mounted navigation and controls. User-perceived latency requires a measured workload.
