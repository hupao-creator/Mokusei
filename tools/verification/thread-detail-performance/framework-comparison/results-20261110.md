# Release Markdown renderer baseline — 2026-11-10

Neither candidate is a demonstrated general replacement for the current renderer.
Textual reduced native view counts substantially but increased mount CPU in all
three workloads. MarkdownUI improved mixed-document mounting and prose/report
scroll CPU, while regressing prose/report mounting. Fewer NSTextViews alone did
not predict lower CPU or memory.

## Scope and identities

Apple M1 Pro, macOS 26.5.1, Swift 6.3.2; Release builds with all three renderers in
the same executable. Production source is `a9cffb62a4f669c2f5b30cf3cd236210bc7c083c`.
Textual is pinned to `01b51875a5406eefc95f52a058cb059e7bc94dc4`; MarkdownUI to
`8371aeb32f35795a9e559029fb08613355733626`. Full identities, fixture hashes and
median/min/max values are in [the aggregate JSON](results-20261110.json).

Three serial fresh-process samples per renderer/workload, 27 total; renderer
order rotates across rounds. Each process mounts twice, scrolls through 120
normalized positions and resizes 900→500→900pt. Timed runs contain no profiler,
accessibility scan or image capture. All timed samples completed their foreground,
thermal, scrolling and restored-height prerequisites. The implementation and
metric definitions are in the [benchmark guide](README.md).

The private report is the same 18-top-level-block source investigated earlier:
14 top-level paragraphs, 27 list paragraphs, 27 markers, 15 table cells and one
code block. Its source and all raw logs remain local. Synthetic prose contains
160 paragraphs; mixed contains 40 sections of headings, prose, lists, tables and
code. No view virtualization is introduced.

## Visual compatibility finding

All nine separate visual samples completed, retaining top/middle/bottom captures.
The mixed fixture contains `| Beta | | 中文🙂 |`: its Status column is deliberately
empty. In the pinned Textual build, the captured row puts `中文🙂` under Status
instead of Notes. Production and MarkdownUI preserve the empty middle cell.
This is a visible table-fidelity failure, not a performance measurement failure;
Textual's mixed results cannot certify a feature-equivalent replacement.

The original native captures are retained unchanged:
[production](evidence/production-mixed.png), [Textual](evidence/textual-mixed.png),
[MarkdownUI](evidence/markdownui-mixed.png). They also show different heading,
table and code styles. No assertion was weakened and no failing frame was removed.

In separate manual native-window checks, a drag from the first paragraph into
the second followed by context-menu Copy produced text from both paragraphs,
including the second paragraph's inline code, in production and Textual. The
same traversal with MarkdownUI selected/copied only the first paragraph. This
is a bounded cross-paragraph interaction observation, not a complete Unicode,
table, keyboard or selection regression suite. Raw clipboard observations remain
local under `/private/tmp/mokusei-markdown-selection-20261110`.

## Interpretation limits and failures

- This isolates public rendering components under a common ScrollView; it does
  not run full Thread navigation, paced admission, line reveal, transport or
  streaming. The earlier Debug application timings are not an A/B baseline for
  these Release component results.
- Body size, requested font, viewport and source bytes match, but renderer
  typography, spacing, code highlighting and local-link preview policies retain
  their defaults. Different document heights are real and visible; the scroll
  distance is normalized to each document. This is not pixel/feature parity.
- Wall convergence includes a 200ms observation floor and 150ms geometry-quiet
  requirement. For the real report, warm wall medians were 228.0 / 288.6 / 310.4ms
  for production / Textual / MarkdownUI; they are not first-pixel timestamps.
- Footprint is a phase-boundary observation, not peak memory. Fresh-process does
  not mean cold operating-system/font caches. Three samples do not establish a
  fleet percentile or a universal speedup/regression.
- Initial app staging failed signing because a SwiftPM resource symlink was
  placed at the bundle root. No timing sample was produced or discarded. Staging
  was corrected, candidate build-directory resource fallbacks were disclosed,
  and all 27 timing samples then completed. The invalid first attempt is retained.
- An initial manual-selection preview blocked while opening its fixture directly
  from Desktop. A process sample located the wait in Foundation's file open;
  staging the same input under `/private/tmp` completed the preview. This was
  separate from every timed/capture run, whose inputs were already staged.
- Final local review canonicalized the launcher's temporary path for PID ownership
  checks and made termination run even if diagnostic sampling fails. A fresh
  six-process launcher run verifies that revision; the benchmark executable is
  unchanged and its results are not pooled with the 27-sample comparison.

No candidate was installed into the production app and no new CI timing gate was
added. Product adoption needs a separate feature-parity and full-reader decision.
