# Chief 产品指南写作

由你撰写面向用户的英文成稿。采用「不懂任何技术，但是很懂当前产品的产品经理」的视角。读者带着一件事来找答案，读完应当知道从哪里开始、怎样操作，以及如何看出操作生效。

## 先核实用户会遇到什么

从[产品指南目录](../../../docs/README.md)找到对应任务，阅读现有页面和所属模块的说明。沿当前版本的实际操作路径核对英文界面文案、控件出现或可用的条件，以及操作产生的结果。名称以界面和本地化文案为准，效果以处理该操作的实现为依据。需要定位交互证据时查[事实与验证索引](../../../tools/verification/facts.md)。

只描述当前已实现的能力。遇到旧文档、设计稿或演示与实现不一致时，先查明差异。若仍无法确认，在交付说明中指出疑点；避免猜测按钮、默认值、成功结果，或把已知缺陷写成产品承诺。声称某条流程经过实测时，核对证据对应的版本和场景。

## 写成用户可以跟做的英文

- 用读者的问题或目标组织页面。直接用 “you” 说明何时使用这项功能，从读者看得见的入口开始，按实际顺序写操作，并告诉读者在哪里看到结果。
- 按钮、菜单和状态沿用实际英文拼写和大小写。用日常动词描述操作。遇到不同选择，解释每个选择对这次任务或后续工作的影响。
- 把会改变下一步的条件放在对应步骤旁，例如所需权限、何时可以继续、失败后能在哪里重试。只有用户确实需要的技术名词、命令、路径或版本要求才进入指南；核实后保留准确写法，并用普通英文解释用途。实现原理、调试、构建、测试和性能测量归所属工程手册。

## 随功能一起维护

功能迭代时，沿受影响的用户任务检查相关页面，在同一变更中更新入口、步骤、可见结果和使用限制。优先修订已有指南；新增任务页面或改变导航时，同步更新目录及相关页面链接。纯内部调整且用户操作与结果相同时，无需改写产品指南。

审阅现有页面和新稿时，从读者的起点走读一遍：读者能否找到文中点名的控件，知道何时可用，并辨认操作结果？核对相对链接，把验证命令和未验证项留在工程记录或交付说明中。
